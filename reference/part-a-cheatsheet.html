CS425 · Part A · Quick Reference

Diagram Cheat Sheet

One running example on every page of your exam prep: the Course Registration System — Enroll in Course. Print this sheet. Review it right before the paper.

The professor's consistency check. The same scenario must tell the same story in every artifact: use-case steps become interaction messages; those messages become class operations and responsibilities; alternative flows must stay visible and consistent.

Time budget for Part A (30–45 min): use-case diagram ≈ 5 min · specification ≈ 8 min · sequence ≈ 10 min · collaboration ≈ 5 min · VOPC ≈ 8 min · subsystem answer ≈ 5 min.

1 · Use-Case Diagram

  • Actors (stick figures) always outside the boundary rectangle; use-case ovals inside.
  • Name use cases verb + noun. Associations are plain solid lines, no arrowheads.
  • «include»: dashed arrow, base → included. Mandatory, always runs.
  • «extend»: dashed arrow, extension → base. Optional; write the condition beside it.
  • External software (payment gateway, email service) is an actor.
flowchart LR
  ST(["🧍 Student"]):::actor
  subgraph SYS["Course Registration System"]
    UC1(["Enroll in Course"])
    UC4(["Verify Prerequisites"])
    UC5(["Join Waitlist"])
    UC1 -. "«include»" .-> UC4
    UC5 -. "«extend» {course is full}" .-> UC1
  end
  ST --- UC1
  classDef actor fill:none;
Lose-marks list: reversed stereotype arrows · actors inside the box · noun-named ovals · ovals for button-level steps.

2 · Use-Case Specification

Write these sections, in this order. Number the main flow. Letter the alternatives.

Name
Enroll in Course
Goal
The student is enrolled in a course section.
Primary actor
Student
Preconditions
The student is authenticated. The course catalog is published.
Trigger
The student selects a course and submits an enrollment request.
Main flow
1. Student selects a course. 2. System verifies prerequisites (BR-1). 3. System checks seat availability. 4. System records the enrollment. 5. System confirms to the student.
Alternative flows
3a. Course is full → system offers the waitlist (the «extend» from the diagram).
Exceptional flows
2a. Prerequisites not met → system rejects the request and shows the missing prerequisite.
Postconditions
An enrollment record exists, or the student is waitlisted, or the request was rejected with a reason.
Business rules
BR-1: a student cannot enroll when prerequisites are not met.

Business rule vs. system behavior: the rule is a policy ("cannot enroll without prerequisites"). The behavior is what the system does about it ("verify, then reject with a message"). Name the rule (BR-1) and cite it inside the flow step where the system checks it.

3 · Analysis Classes (Use-Case Realization)

StereotypeResponsibilityThis example
«boundary»Talks to the actor. One per actor–use-case pair. No business logic.EnrollmentForm
«control»Coordinates the use-case flow. Applies business rules. Usually one per use case.EnrollmentController
«entity»Holds the domain data and the rules that belong to that data.Student, Course, Enrollment

On paper you may draw the RUP symbols or a class box with the stereotype in guillemets — both are accepted. RUP symbols: boundary = a circle with a vertical bar on its left; control = a circle with an arrowhead on top; entity = a circle resting on a horizontal line.

Responsibility-driven assignment: ask "who has the data?" (entity), "who coordinates?" (control), "who faces the actor?" (boundary). In design, the analysis classes refine into UI classes, services/controllers, and entities + DAOs — behavior must not get lost in that refinement.

4 · Sequence Diagram

  • Left-to-right order: actor · boundary · control/service · repository/DAO · entity.
  • Solid arrow = call. Dashed arrow = return. Draw activation bars for every call.
  • Business-rule validation goes on the control (flow rules) or the entity (data rules) — never on the boundary.
  • Simple rule → one conditional message with a guard like [seats available]. Complex alternative flow → an alt frame, or a separate sequence diagram for that flow.
sequenceDiagram
  actor S as Student
  participant F as «boundary» :EnrollmentForm
  participant C as «control» :EnrollmentController
  participant R as «DAO» :CourseRepository
  participant E as «entity» :Enrollment
  S->>+F: submitEnrollment(courseId)
  F->>+C: enroll(studentId, courseId)
  C->>+R: findCourse(courseId)
  R-->>-C: course
  C->>C: verifyPrerequisites(student, course) [BR-1]
  alt prerequisites met
    C->>+E: create(student, course)
    E-->>-C: enrollment
    C-->>F: confirmation
  else prerequisites not met
    C-->>F: error: missing prerequisite
  end
  deactivate C
  F-->>-S: show result
Lose-marks list: boundary class doing validation · missing return arrows · participants in random order · a message with no matching use-case step.

5 · Collaboration (Communication) Diagram

  • Same story as the sequence diagram, different emphasis: object links instead of time order.
  • Objects are boxes named :EnrollmentForm; lines between them are structural links.
  • Write messages along the links with nested numbers: 1, then 1.1, 1.2 inside it, then 1.1.1 deeper. The numbering carries the order and the nesting.
  • Show validation and alternatives with guards: 1.2 [prerequisites met]: create(...).
flowchart LR
  S["🧍 Student"]:::actor
  F[":EnrollmentForm"]
  C[":EnrollmentController"]
  R[":CourseRepository"]
  E[":Enrollment"]
  S ---|"1: submitEnrollment(courseId)"| F
  F ---|"1.1: enroll(studentId, courseId)"| C
  C ---|"1.1.1: findCourse(courseId)"| R
  C ---|"1.1.2: verifyPrerequisites() [BR-1]"| C
  C ---|"1.1.3 [prereqs met]: create(student, course)"| E
  classDef actor fill:none;

Convert from the sequence diagram: each call keeps its receiver, and the lifeline order becomes the number nesting. Nothing new is invented here.

6 · VOPC — View of Participating Classes

  • One class diagram per use-case realization: all classes that appear in the interaction diagrams.
  • Show stereotypes, key attributes, operations, associations, dependencies, multiplicities.
  • Derive every operation from a message: if the controller receives enroll(...) in the sequence diagram, then EnrollmentController must list enroll(...). No message, no operation. No operation, no message.
classDiagram
  class EnrollmentForm["«boundary» EnrollmentForm"]
  EnrollmentForm : +submitEnrollment(courseId)
  class EnrollmentController["«control» EnrollmentController"]
  EnrollmentController : +enroll(studentId, courseId)
  EnrollmentController : -verifyPrerequisites(student, course)
  class CourseRepository["«DAO» CourseRepository"]
  CourseRepository : +findCourse(courseId) Course
  class Student["«entity» Student"]
  Student : -studentId
  Student : -completedCourses
  class Course["«entity» Course"]
  Course : -courseId
  Course : -capacity
  Course : -prerequisites
  class Enrollment["«entity» Enrollment"]
  Enrollment : -status
  Enrollment : +create(student, course)
  EnrollmentForm ..> EnrollmentController : uses
  EnrollmentController ..> CourseRepository : uses
  EnrollmentController ..> Enrollment : creates
  Student "1" -- "0..*" Enrollment
  Course "1" -- "0..*" Enrollment
Lose-marks list: operations that no message justifies · messages with no operation · missing multiplicities on entity associations · boundary classes linked directly to entities (they must go through the control).

7 · Subsystem Design

RoleResponsibilityThis example
FaçadeOne entry point that hides the subsystem's internals. Callers see the interface only.EnrollmentFacade / IEnrollmentService
ServiceImplements one area of use-case logic behind the façade.EnrollmentService, WaitlistService
DAOData access for one entity; hides SQL/persistence details.CourseDAO
RepositoryCollection-like access to entities; a domain-flavored DAO.CourseRepository
  • Encapsulation / information hiding: callers depend on the subsystem's interface, never on its internal classes.
  • Dependency reduction: UI → façade interface → services → repositories. Arrows point one way, downward.
  • To show subsystem behavior, reuse the same views: a sequence diagram of a call through the façade, and a class diagram of the interface plus its realizing classes.
