Draw a Sequence Diagram

≈ 30 minutes · pen and paper required at the end · cheat sheet · ← Lesson 3

Why this lesson. The sequence diagram is where the consistency check bites hardest: every message must come from a specification step, and every receiver must be a class from your realization. You already built both inputs.

What the exam asks

  • Show actors, lifelines, activation bars, messages, return messages, and the correct order.
  • Include architectural participants: boundary/controller, control/service, repository/DAO, entities.
  • Show business-rule validation and explain where each check belongs.
  • Simple rule → one clear conditional message. Complex alternative flow → a separate sequence diagram.
  • Stay consistent with the use-case flow and the class responsibilities.

The notation, piece by piece

ElementOn paper, draw…Rule
ParticipantA box at the top, named :EnrollmentForm (colon = an object, not the class). The actor is a stick figure.Order left → right: actor · boundary · control · DAO · entity.
LifelineA dashed vertical line falling from each box.Time flows downward. Never draw a message that goes up.
Activation barA thin rectangle on the lifeline.Starts when the object receives a call; ends when it returns.
MessageA solid arrow with a filled head, labeled verb(args).The label becomes an operation of the receiver (Lesson 6).
ReturnA dashed arrow back, labeled with the result.Every call that yields a value returns. Close what you open.
Self-messageA small arrow that loops back to the same lifeline.Use it when an object runs its own check.
Guard[seats free] before a message label.A simple condition on one message.
alt / opt frameA rectangle around the branch, label alt with a divider, or opt for a single optional part.Use for a branch of a few messages. Bigger than that → separate diagram.

Build one in six moves

Input: the Enroll in Course specification (Lesson 2) and the realization classes (Lesson 3). We draw the main flow plus the BR-1 branch.

1

Line up the participants

Write the actor first, then the classes from your realization, in call order: boundary, control, DAO, entities. Drop the lifelines. A good line-up earns marks before a single message exists.

sequenceDiagram
  actor S as Student
  participant F as «boundary» :EnrollmentForm
  participant C as «control» :EnrollmentController
  participant R as «DAO» :CourseRepository
  participant K as «entity» :Course
  participant E as «entity» :Enrollment
2

Start with the trigger

Spec trigger: the student submits an enrollment request. Draw a solid arrow from the actor to the boundary and start the boundary's activation bar.

sequenceDiagram
  actor S as Student
  participant F as «boundary» :EnrollmentForm
  S->>+F: submitEnrollment(courseId)
  note over F: the activation bar stays open until the final return
  deactivate F
3

The boundary delegates — one message, no logic

The form immediately hands the request to the control. That single message is the whole job of the boundary until the result comes back.

If your form sends more than one business message, logic leaked into the boundary. Red pen territory.

sequenceDiagram
  actor S as Student
  participant F as «boundary» :EnrollmentForm
  participant C as «control» :EnrollmentController
  S->>+F: submitEnrollment(courseId)
  F->>+C: enroll(studentId, courseId)
  deactivate C
  deactivate F
4

The control fetches data through the DAO

The controller needs the course to run any check. It asks the repository, and the repository returns the entity. Draw the return as a dashed arrow — and close the DAO's activation bar with it.

sequenceDiagram
  actor S as Student
  participant C as «control» :EnrollmentController
  participant R as «DAO» :CourseRepository
  activate C
  C->>+R: findCourse(courseId)
  R-->>-C: course
  deactivate C
5

Place the business-rule checks where they belong

Spec step 2 checks BR-1. The control coordinates; the entity answers from its own data. So: the controller sends checkPrerequisites(student) to the Course entity, and the entity returns the verdict. A rule about one object's own data can also be a self-message on that object.

CheckBelongs onWhy
BR-1 prerequisitesCourse (asked by the control)Course owns its prerequisite list.
BR-2 seat availabilityCourse (asked by the control)Course owns capacity and count.
Flow decision (reject / continue / waitlist)EnrollmentControllerThe control owns the branching of the flow.
sequenceDiagram
  participant C as «control» :EnrollmentController
  participant K as «entity» :Course
  activate C
  C->>+K: checkPrerequisites(student)
  K-->>-C: met / not met  [BR-1]
  deactivate C
6

Branch, then return all the way back

BR-1 has two outcomes, so wrap them in an alt frame. Inside the met branch: check seats with a guard, create the enrollment, confirm. Then send every return, from the deepest object back to the actor. The complete diagram:

sequenceDiagram
  actor S as Student
  participant F as «boundary» :EnrollmentForm
  participant C as «control» :EnrollmentController
  participant R as «DAO» :CourseRepository
  participant K as «entity» :Course
  participant E as «entity» :Enrollment
  S->>+F: submitEnrollment(courseId)
  F->>+C: enroll(studentId, courseId)
  C->>+R: findCourse(courseId)
  R-->>-C: course
  C->>+K: checkPrerequisites(student)
  K-->>-C: met / not met  [BR-1]
  alt prerequisites met
    C->>+K: hasFreeSeat()
    K-->>-C: seats free  [BR-2]
    C->>+E: create(student, course)
    E-->>-C: enrollment
    C-->>F: confirmation
  else prerequisites not met
    C-->>F: rejection: missing prerequisite
  end
  deactivate C
  F-->>-S: show result

Simple rule vs. complex flow

The guide draws a sharp line, and the exam tests it:

  • Simple rule — one check, one branch point: a guard on the message ([seats free] create(...)) or a small alt frame. Keep it in the main diagram.
  • Complex alternative flow — several checks and messages of its own: give that flow its own sequence diagram, titled with the flow number. The main diagram stays readable.

Flow 3a (course full → waitlist) has its own steps, so it gets its own diagram:

sequenceDiagram
  participant F as «boundary» :EnrollmentForm
  participant C as «control» :EnrollmentController
  participant K as «entity» :Course
  note over F,K: Alternative flow 3a — the course is full
  activate C
  C-->>F: offer waitlist
  F->>C: acceptWaitlist()
  C->>+K: addToWaitlist(student)
  K-->>-C: position
  C-->>F: waitlisted at position
  deactivate C

Grade your own diagram with this table: a spec step with no message, or a message with no step, is a lost mark.

Red-pen list: how students lose marks here

  • Missing returns. A call that fetches data must return. Close every activation bar.
  • Chatty boundary. The form sends one business message: enroll(...). It never calls a DAO or an entity.
  • Wrong participant order. Actor · boundary · control · DAO · entity, left to right.
  • Class names without colons. Lifelines are objects: :Course, not Course.
  • Invented messages. Every message maps to a spec step. Extras break consistency.
  • The mega-diagram. A complex alternative flow squeezed into nested alt frames. Split it out.
  • Validation in the wrong place. The entity answers about its own data; the control decides the branch; the boundary shows the outcome.

Quick check

1 · Solid arrow with a filled head vs. dashed arrow — which is which?

Solid arrows carry operations; dashed arrows carry results back. Both are graded.

2 · Where does the BR-1 prerequisite verdict come from?

Same answer as Lesson 3, now drawn: control coordinates, entity owns the data rule, DAO only fetches.

3 · Flow 3a (waitlist) has four messages of its own. How do you show it?

The guide's own rule: a simple rule gets a conditional message; a complex alternative flow gets its own diagram. Alternative flows must stay visible.

4 · Which participant order is correct, left to right?

Follow the call chain: actor, boundary, control, DAO, entities. Messages then flow rightward and returns flow leftward.

5 · Your diagram has a message "logEnrollmentAttempt()" but the specification never mentions it. What does the grader see?

The consistency check runs both directions: use-case steps become messages, and messages must trace back to steps.

Now draw on paper

Set a 10-minute timer. Draw the sequence diagram for the Borrow Book main flow (Lesson 2 spec, Lesson 3 classes: KioskUI, LoanController, Member, Book, Loan — add MemberRepository as the DAO). Show BR-1 and BR-2 as checks in the right places, with the BR-1 failure in an alt frame. Decide: does flow 4a need its own diagram, or is a branch enough?

Open the model answer 
sequenceDiagram
  actor M as Member
  participant U as «boundary» :KioskUI
  participant C as «control» :LoanController
  participant R as «DAO» :MemberRepository
  participant B as «entity» :Member
  participant L as «entity» :Loan
  M->>+U: scanCard(cardId)
  U->>+C: startBorrow(cardId)
  C->>+R: findMember(cardId)
  R-->>-C: member
  C->>+B: isValid()
  B-->>-C: valid / expired  [BR-1]
  alt membership valid
    M->>U: scanBook(bookId)
    U->>C: borrow(bookId)
    C->>+B: canTakeAnotherLoan()
    B-->>-C: yes / limit reached  [BR-2]
    C->>+L: create(member, book)  [BR-3: due in 21 days]
    L-->>-C: loan with due date
    C-->>U: due date
  else membership invalid
    C-->>U: rejection: invalid membership
  end
  deactivate C
  U-->>-M: show result

Flow 4a (loan limit reached): one check, one refusal message — a simple rule. A small alt around the create step is enough; no separate diagram is needed. Flow 6a (more books) repeats steps 3–6; on paper, a loop frame around the scan-and-create part, or a note "repeat for each book", both score.

Grade yourself

  • Participant order: Member · :KioskUI · :LoanController · :MemberRepository · :Member · :Loan.
  • Activation bars on every participant that does work; every bar closed by a return.
  • KioskUI sends business messages only to the controller.
  • BR-1 answered by the Member entity; BR-2 by the Member entity; the branch decided by the controller.
  • BR-1 failure inside an alt frame; a final return reaches the actor in both branches.
  • Every message traces to a step of your Lesson 2 specification.

Score 5–6: say "next" for Lesson 5. Score ≤ 4: redraw once with the consistency table beside you.
