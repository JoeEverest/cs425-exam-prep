Design a Subsystem

≈ 25 minutes · pen and paper required at the end · cheat sheet · ← Lesson 6

Why this lesson. Subsystem questions are explain-and-justify questions: the marks sit in the vocabulary (encapsulation, information hiding, dependency reduction) and in the four pattern roles. The drawing part reuses the views you already own — a class view and a sequence view.

What the exam asks

  • Define subsystem responsibilities and interfaces; explain how they support use-case behavior.
  • Apply encapsulation, information hiding, and dependency reduction.
  • Recognize the roles: façade, service, DAO, repository.
  • Model subsystem operations with sequence, collaboration, and class views where required.

Three principles, exam-ready

Learn one sentence and one consequence for each. The sentence defines; the consequence proves you understand.

PrincipleOne sentenceThe consequence to add
EncapsulationThe subsystem bundles its classes and exposes only one interface.Callers see operations, never classes.
Information hidingCallers cannot see or depend on the subsystem's internals.The internals can change — a new database, a rewritten service — and no caller breaks.
Dependency reductionMany clients depend on one interface instead of many internal classes.The dependency arrows point one way: UI → interface → services → repositories. No cycles.

The four roles

RoleJobWhat it never doesSpot it by
FaçadeThe single entry point. Receives every external call and delegates inward.Business logic. It routes; it does not decide.One operation per use case: enroll(...), joinWaitlist(...).
ServiceImplements the use-case logic behind the façade — your Lesson 3 control, promoted.Talk to the UI, or write SQL.Coordinates entities and repositories; owns the flow.
DAOPersistence operations for one entity: find, save, delete.Business decisions; leaking SQL types to callers.Named XxxDAO; operations mirror storage actions.
RepositoryA collection-like, domain-flavored view of entities: "give me the course", "add this enrollment".Expose rows, tables, or query language.Named XxxRepository; speaks in domain objects.

DAO vs. repository in one line: the DAO speaks the storage's language for one entity; the repository speaks the domain's language for a collection. Both hide persistence, and many courses use the names interchangeably — follow the professor's wording in the question.

Build the Enrollment subsystem in four moves

1

Name the subsystem and its interface

Responsibility first, in one sentence: "the Enrollment subsystem manages course enrollments, waitlists, and prerequisite checking." Then give it one provided interface, IEnrollmentService, listing one operation per use-case entry point.

2

Put the façade behind the interface

EnrollmentFacade realizes IEnrollmentService. Its body is thin: each operation delegates to a service. On paper, draw realization as a dashed line with a hollow triangle pointing at the interface.

3

Arrange the internals — arrows point one way

Behind the façade: the service (your Lesson 3 controller, now inside), the repositories, and the entities. Check every arrow: nothing inside points out to the UI, and nothing outside points past the interface.

The client's world ends at the interface. Everything inside the box is invisible to it — that is information hiding, drawn.

4

Show the behavior with views you already own

The exam says "model subsystem operations using sequence, collaboration, and class-based views where required." Two views usually suffice:

Class view — the interface, its realization, and the internal dependencies:

classDiagram
  class IEnrollmentService["«interface» IEnrollmentService"]
  IEnrollmentService : +enroll(studentId, courseId)
  IEnrollmentService : +joinWaitlist(studentId, courseId)
  IEnrollmentService : +drop(studentId, courseId)
  class EnrollmentFacade["EnrollmentFacade"]
  class EnrollmentService["EnrollmentService"]
  EnrollmentService : +enroll(studentId, courseId)
  class CourseRepository["«DAO» CourseRepository"]
  CourseRepository : +findCourse(courseId) Course
  class RegistrationUI["RegistrationUI (client)"]
  RegistrationUI ..> IEnrollmentService : uses
  EnrollmentFacade ..|> IEnrollmentService
  EnrollmentFacade ..> EnrollmentService : delegates
  EnrollmentService ..> CourseRepository : uses

Sequence view — one call through the façade. Note how short the client's part is: one message in, one result out.

sequenceDiagram
  participant U as :RegistrationUI
  participant FA as :EnrollmentFacade
  participant SV as :EnrollmentService
  participant CR as «DAO» :CourseRepository
  U->>+FA: enroll(studentId, courseId)
  FA->>+SV: enroll(studentId, courseId)
  SV->>+CR: findCourse(courseId)
  CR-->>-SV: course
  note over SV: the Lesson 4 interaction runs here - checks BR-1, BR-2, creates the Enrollment
  SV-->>-FA: confirmation
  FA-->>-U: confirmation
  note over U: the client never saw a repository or an entity

And the justification sentence the grader wants: the subsystem supports the use-case behavior because each interface operation corresponds to a use case, and its realization inside is exactly the use-case realization from Lessons 3–6.

Red-pen list: how students lose marks here

  • The bypass arrow. UI → CourseRepository directly. One arrow past the interface destroys the whole answer.
  • A thick façade. Business rules inside the façade. It delegates; the service decides.
  • Two-way arrows. A repository that calls the service back, or an entity that knows the UI. Dependencies point one way.
  • A CRUD interface. IEnrollmentService with getCourse/setCourse/updateStudent. Interface operations mirror use cases, not tables.
  • Leaky persistence. A repository returning rows or result sets. It returns domain objects.
  • Definitions without consequences. "Encapsulation means hiding" earns half marks. Add what it buys: internals can change without breaking callers.

Quick check

1 · Which name may appear in the client's code?

Encapsulation: the client depends on the interface and nothing else. Every internal name in client code is a bypass.

2 · The team replaces the database and rewrites both repositories. No client changes. Which principle did the work?

That consequence is the whole point of the principle — and the sentence the grader looks for.

3 · Where does the BR-1 prerequisite decision run in the subsystem?

Same placement logic since Lesson 3: the coordinator decides, the entity answers, persistence only fetches. The façade is thin.

4 · "Give me the member for this card" returning a Member object, no SQL visible. Which role?

Domain-language access to stored entities is the repository/DAO job. The caller sees domain objects, never rows.

5 · The question says "model the subsystem operation enroll". What do you draw?

The guide names the views: sequence, collaboration, and class-based. You already know all three; only the participants changed.

Now draw on paper

Set an 8-minute timer. Design the Lending subsystem for the library: one sentence of responsibility, the interface, the class view, and a short sequence view of borrowBook through the façade. Then write two sentences: one for information hiding, one for dependency reduction, each with its consequence.

Open the model answer

Responsibility: the Lending subsystem manages loans: borrowing, returning, late fees, and the loan rules BR-1..3.

classDiagram
  class ILendingService["«interface» ILendingService"]
  ILendingService : +borrowBook(cardId, bookId)
  ILendingService : +returnBook(bookId)
  ILendingService : +payLateFee(loanId)
  class LendingFacade["LendingFacade"]
  class LoanService["LoanService"]
  LoanService : +borrow(cardId, bookId)
  class MemberRepository["«DAO» MemberRepository"]
  MemberRepository : +findMember(cardId) Member
  class LoanRepository["«DAO» LoanRepository"]
  LoanRepository : +save(loan)
  class KioskUI["KioskUI (client)"]
  KioskUI ..> ILendingService : uses
  LendingFacade ..|> ILendingService
  LendingFacade ..> LoanService : delegates
  LoanService ..> MemberRepository : uses
  LoanService ..> LoanRepository : uses

sequenceDiagram
  participant U as :KioskUI
  participant FA as :LendingFacade
  participant SV as :LoanService
  participant MR as «DAO» :MemberRepository
  participant LR as «DAO» :LoanRepository
  U->>+FA: borrowBook(cardId, bookId)
  FA->>+SV: borrow(cardId, bookId)
  SV->>+MR: findMember(cardId)
  MR-->>-SV: member
  note over SV: BR-1 and BR-2 checks with the member's data - Loan created (BR-3)
  SV->>+LR: save(loan)
  LR-->>-SV: saved
  SV-->>-FA: due date
  FA-->>-U: due date

Information hiding: KioskUI depends only on ILendingService, so the loan rules, the repositories, and the storage can change without any change to the kiosk. Dependency reduction: every client depends on one interface instead of five internal classes, and all arrows point one way — UI → interface → service → repositories.

Grade yourself

  • One responsibility sentence; one interface with use-case operations, not CRUD.
  • Realization drawn correctly: LendingFacade — dashed line, hollow triangle — ILendingService.
  • Façade delegates; the BR checks run in LoanService with entity data.
  • No arrow bypasses the interface; no arrow points outward.
  • Sequence view shows one message in, one result out for the client.
  • Both principle sentences include their consequence.

Score 5–6: say "next" for Lesson 8, the timed mock. Score ≤ 4: rewrite the two principle sentences and redraw the class view only.
