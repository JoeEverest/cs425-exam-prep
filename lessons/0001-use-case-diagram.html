CS425 · Part A · Lesson 1 of 8

Draw a Use-Case Diagram

≈ 20 minutes · pen and paper required at the end · open the Part A cheat sheet

Why this lesson. The exam guide lists use-case modeling first. Every later artifact (sequence, collaboration, VOPC) must stay consistent with this diagram. Learn it first, and the rest of Part A has a skeleton to hang on.

What the exam asks

  • Identify actors, use cases, the system boundary, and actor–use-case associations.
  • Use «include» and «extend» only when they are needed.
  • Show what the system must do, not how the software will do it.

The notation, piece by piece

Mermaid draws these shapes in a hand-drawn style below. On paper, use the exact UML shapes in this table.

ElementOn paper, draw…Rule
ActorA stick figure with the name below it. An actor is a role or an external system. It is always outside the boundary.
Use caseAn oval with the name inside. Name it as a verb + noun: Enroll in Course, not Enrollment.
System boundaryA rectangle around all use cases, name at the top. Use cases go inside. Actors stay outside.
AssociationA plain solid line, actor to oval. No arrowhead is needed on an association.
«include»A dashed arrow, base → included, labeled «include». Mandatory. The base use case always runs the included one.
«extend»A dashed arrow, extension → base, labeled «extend». Optional. Write the condition next to the arrow, e.g. {course is full}.

Arrow memory trick: the base points at «include» (it needs it), but the «extend» points at the base (the extra knocks on the base's door).

Build one in six moves

Scenario for this lesson: a university course registration system. Students enroll in courses, drop courses, and pay tuition through an external payment gateway. A registrar can also drop a student. The system always verifies prerequisites before an enrollment. When a course is full, the student can join a waitlist instead.

5

Add «include» for mandatory shared behavior

The scenario says the system always verifies prerequisites before an enrollment. "Always" signals «include». Draw a dashed arrow from Enroll in Course to Verify Prerequisites and label it «include».

The base points at the thing it needs.

6

Add «extend» for optional, conditional behavior

Joining the waitlist happens only when the course is full. A condition signals «extend». Draw a dashed arrow from Join Waitlist to Enroll in Course, label it «extend», and write the condition beside it.

Note the flipped direction: the extension points at the base.

Red-pen list: how students lose marks here

  • Reversed arrows. «include» goes base → included. «extend» goes extension → base. Graders check this first.
  • Actors inside the boundary. An actor is never inside the rectangle.
  • Noun names. "Enrollment" is not a use case. "Enroll in Course" is.
  • Step decomposition. "Enter password", "Click submit" are steps of a flow, not use cases. Keep ovals at the goal level.
  • «include» for optional behavior. If there is a condition, it is «extend».
  • Arrowheads on associations. An actor line is plain. Save arrows for the dashed stereotypes.

Quick check

Answer each question. You get the reason immediately.

1 · "Enroll in Course" always runs "Verify Prerequisites". Which arrow is correct?

The base use case points at the behavior it includes. Mandatory + shared = «include», base → included.

2 · "Join Waitlist" happens only when the course is full. Which arrow is correct?

«extend» reverses the direction: the extension points at the base. The condition belongs next to the arrow.

3 · The system sends card payments to an external payment service. How do you model that service?

An actor is anything outside the system that interacts with it. External software qualifies.

4 · Which is a correctly named use case?

Verb + noun, one goal, one sitting. "Course" is an entity. "Enrollment Management" is a vague noun phrase.

5 · The scenario says "a student cannot enroll when prerequisites are not met." Where does this rule live?

The guide separates business rules from what the system does. The diagram stays at the goal level; rules and validations live in the specification's flows.

Now draw on paper

Set a 5-minute timer. Draw a use-case diagram for this scenario, then open the model answer and grade yourself.

Library Lending System. Members borrow and return books at a self-service kiosk. Before a member borrows a book, the system always verifies the membership. When a returned book is overdue, the member can also pay a late fee; the system confirms that payment through an external payment service. A librarian registers new members.

Open the model answer 
flowchart LR
  ME(["🧍 Member"]):::actor
  LB(["🧍 Librarian"]):::actor
  subgraph SYS["Library Lending System"]
    B(["Borrow Book"])
    V(["Verify Membership"])
    R(["Return Book"])
    F(["Pay Late Fee"])
    G(["Register Member"])
    B -. "«include»" .-> V
    F -. "«extend» {book is overdue}" .-> R
  end
  PS(["🖥 Payment Service"]):::actor
  ME --- B
  ME --- R
  LB --- G
  F --- PS
  classDef actor fill:none;

Grade yourself

  • Boundary rectangle with the system name at the top.
  • Member, Librarian, and Payment Service outside the boundary.
  • Five ovals, each named verb + noun.
  • Plain association lines: Member–Borrow, Member–Return, Librarian–Register Member, Payment Service–Pay Late Fee.
  • «include» arrow from Borrow Book → Verify Membership ("always" in the scenario).
  • «extend» arrow from Pay Late Fee → Return Book, with {book is overdue} beside it.
  • No arrowheads on association lines. No actors inside the box.

Score 6–7: move to lesson 2. Score 4–5: redraw once, arrows only. Score ≤ 3: reread the six moves, then redraw the whole thing.

Stuck on anything? Ask your teacher in the Claude Code session — for example: "why is Verify Membership not connected to the Member actor?"
