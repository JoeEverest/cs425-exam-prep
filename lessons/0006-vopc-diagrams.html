Draw a VOPC Diagram

≈ 25 minutes · pen and paper required at the end · cheat sheet · ← Lesson 5

Why this lesson. VOPC = View of Participating Classes: one class diagram per use-case realization. It is the harvest of Lessons 3–5 — and the grader's favorite place to run the consistency check, because every operation must trace back to a message.

What the exam asks

  • Identify the View of Participating Classes for a use-case realization.
  • Show class names, stereotypes, key attributes, operations, associations, dependencies, and multiplicities.
  • Derive operations and responsibilities from the messages in the interaction diagrams.
  • Check consistency among use case, sequence diagram, collaboration diagram, and VOPC.

The one rule that generates the whole diagram

Message → operation on the receiver. If any interaction diagram shows a message m(...) arriving at :X, then class X lists operation m(...). No message, no operation. No operation, no message.

Everything else is bookkeeping: attributes are the data a class needed to answer its messages, and the relationships are the links your collaboration diagram already drew.

The notation, piece by piece

ElementOn paper, draw…Rule
Class boxA rectangle with three compartments: name (with «stereotype»), attributes, operations.Class names now, no colons — this is a class diagram, not objects.
Visibility+ public, - private before each member.Operations that receive messages are +; internal data is -.
AssociationA solid line between entity classes.Structural, long-lived; write multiplicities at both ends.
DependencyA dashed arrow, «uses» or «creates».For boundary → control, control → DAO, control → entity traffic.
Multiplicity1, 0..1, 0..* at the line ends.Read each end from the far side: one Student has 0..* Enrollments.

Build it in five moves

Input: the sequence diagram (Lesson 4), the 3a waitlist diagram, and the collaboration diagram (Lesson 5).

1

One box per participant

Copy every participant from the interaction diagrams — the actor stays out. Keep the stereotypes: «boundary», «control», «DAO», «entity».

classDiagram
  class EnrollmentForm["«boundary» EnrollmentForm"]
  class EnrollmentController["«control» EnrollmentController"]
  class CourseRepository["«DAO» CourseRepository"]
  class Student["«entity» Student"]
  class Course["«entity» Course"]
  class Enrollment["«entity» Enrollment"]
2

Harvest the operations from the messages

Walk every message in every interaction diagram — the 3a waitlist diagram too — and write it on its receiver. This table is your worksheet:

Message (from Lessons 4–5)ReceiverOperation on
submitEnrollment(courseId):EnrollmentFormEnrollmentForm
enroll(studentId, courseId):EnrollmentControllerEnrollmentController
findCourse(courseId):CourseRepositoryCourseRepository
checkPrerequisites(student) [BR-1]:CourseCourse
hasFreeSeat() [BR-2]:CourseCourse

addToWaitlist(student) — flow 3a:CourseCourse

The alternative flow's operations count too. Forgetting addToWaitlist is the classic slip.

3

Add the key attributes

Ask each entity: "what data did you need to answer your messages?" Course answered BR-1 and BR-2, so it holds prerequisites, capacity, and the enrolled count. Student's completed courses fed the BR-1 check. Keep attributes private.

4

Draw the relationships

Two kinds, and the split matters:

  • Dependencies (dashed): the traffic routes — form «uses» controller, controller «uses» repository and Course, controller «creates» Enrollment. These mirror your collaboration links.
  • Associations (solid, with multiplicities): the domain structure — a Student holds 0..* Enrollments; a Course holds 0..* Enrollments.
5

Assemble and sweep

The complete VOPC for Enroll in Course:

classDiagram
  class EnrollmentForm["«boundary» EnrollmentForm"]
  EnrollmentForm : +submitEnrollment(courseId)
  class EnrollmentController["«control» EnrollmentController"]
  EnrollmentController : +enroll(studentId, courseId)
  class CourseRepository["«DAO» CourseRepository"]
  CourseRepository : +findCourse(courseId) Course
  class Student["«entity» Student"]
  Student : -studentId
  Student : -completedCourses
  class Course["«entity» Course"]
  Course : -prerequisites
  Course : -capacity
  Course : -enrolledCount
  Course : +checkPrerequisites(student) bool
  Course : +hasFreeSeat() bool
  Course : +addToWaitlist(student) int
  class Enrollment["«entity» Enrollment"]
  Enrollment : -status
  Enrollment : -date
  Enrollment : +create(student, course)
  EnrollmentForm ..> EnrollmentController : uses
  EnrollmentController ..> CourseRepository : uses
  EnrollmentController ..> Course : uses
  EnrollmentController ..> Enrollment : creates
  Student "1" -- "0..*" Enrollment
  Course "1" -- "0..*" Enrollment

Now sweep it against the worksheet from move 2: seven messages, seven operations, each on the right class. Then sweep the reverse direction: no class lists an operation the worksheet does not contain.

The four-artifact consistency check

This is the check your professor printed in a box. Run it as four questions:

#QuestionWhere it fails
1Does every use-case step map to at least one message?A spec step nobody draws — often the confirmation.
2Do the sequence and collaboration diagrams show the same messages, receivers, and guards?Story drift during conversion.
3Does every message appear as an operation on its receiver in the VOPC?Forgotten alternative-flow operations.
4Does every VOPC operation trace back to a message?Invented operations like getters "for completeness".

In the exam, run this sweep in the last five minutes of Part A. It converts silent errors into quick fixes.

Red-pen list: how students lose marks here

  • Orphan operations. An operation no message justifies. Getters and setters "for completeness" are the usual offenders.
  • Missing 3a operations. addToWaitlist exists only in the separate flow diagram — it still belongs in the VOPC.
  • Object names in a class diagram. :Course is an object. Here it is Course.
  • No multiplicities. Entity associations without numbers are half-drawn.
  • Boundary wired to entities. Same rule since Lesson 3 — the dependency arrows must respect it.
  • Attributes on the controller. A control coordinates; capacity and prerequisites live on Course.

Quick check

1 · The sequence diagram shows checkPrerequisites(student) arriving at :Course. Where does the operation go?

The receiver rule. The sender gains nothing; the receiver gains the operation.

2 · Your VOPC lists EnrollmentController.notifyStudent(), but no diagram shows that message. What is it?

Check 4 of the sweep: every operation traces back to a message. Extras are errors, not effort.

3 · Student–Enrollment vs. EnrollmentForm–EnrollmentController. Which lines do you draw?

Entities relate structurally and long-term — association. The boundary merely calls the controller during the use case — dependency.

4 · Read: Student "1" — "0..*" Enrollment.

Read each end from the opposite side: stand at Student, look across, see 0..*; stand at Enrollment, look across, see 1.

5 · Why does Course hold -capacity and -prerequisites?

Attributes are derived the same way operations are: from what the messages demanded. Data follows responsibility.

Grade yourself

  • Six classes, stereotyped, class names without colons.
  • Every message from Lessons 4–5 appears as an operation on its receiver — scanCard and scanBook both on KioskUI.
  • No orphan operations, no getters "for completeness".
  • Member's attributes justify isValid() and canTakeAnotherLoan(); Loan holds the due date (BR-3).
  • Dashed «uses»/«creates» for the traffic; solid associations with multiplicities between entities.
  • The four-question sweep passes in both directions.

Score 5–6: say "next" for Lesson 7. Score ≤ 4: redo the harvest table first — the diagram falls out of it.
