Write a Use-Case Specification

≈ 25 minutes · pen and paper required at the end · cheat sheet · ← Lesson 1

Why this lesson. The specification is the script for everything that follows. In Lesson 4, each numbered step becomes a message in the sequence diagram. If a step is missing here, the consistency check fails there.

What the exam asks

  • Write a complete specification: name, goal, primary actor, preconditions, postconditions, trigger, main flow, alternative flows, exceptional flows.
  • Recognize business rules and validation requirements inside the flows.
  • Separate what the system must do from how the software will implement it.

Three distinctions that carry the marks

DistinctionTest questionExample
Precondition vs. trigger Is it a state that must already be true, or the event that starts the use case? "Student is authenticated" = precondition. "Student submits an enrollment request" = trigger.
Alternative vs. exceptional flow Does the path still reach an acceptable outcome, or does the goal fail? Course full → waitlist = alternative. Prerequisites not met → rejection = exceptional.
What vs. how Would the sentence still be true with a different technology? "System records the enrollment" = what ✓. "System inserts a row into the enrollments table" = how ✗.

A business rule is a policy that exists without the software: "a student cannot enroll without the prerequisites." Name it (BR-1) and cite it in the step that checks it.

Build one in six moves

Same scenario as Lesson 1: Enroll in Course in the Course Registration System. Watch the specification grow, section by section.

1

Frame it: name, goal, primary actor

Copy the name from the oval in your use-case diagram — the two artifacts must match, word for word. The goal is the outcome, written from the actor's view.

Name
Enroll in Course
Goal
The student is enrolled in a course section.
Primary actor
Student
2

Bound it: preconditions, trigger, postconditions

Preconditions are states that hold before the use case starts. The trigger is the single event that starts it. Postconditions must cover every ending — success, alternative, and failure.

Preconditions
The student is authenticated. The course catalog is published.
Trigger
The student submits an enrollment request for a selected course.
Postconditions
Success: an enrollment record exists. Alternative: the student is on the waitlist. Failure: no enrollment exists and the student saw the reason.
3

Write the main flow — the happy path only

Number every step. Alternate between "the actor does X" and "the system does Y". No conditions, no failures, no technology. Save the branches for moves 4 and 5.

Each step here becomes a message in Lesson 4. Write steps you would want to draw.

Main flow
  1. The student selects a course from the catalog.
  2. The system verifies the prerequisites [BR-1].
  3. The system checks seat availability.
  4. The system records the enrollment.
  5. The system confirms the enrollment and shows the section details.
4

Add alternative flows — other roads to an acceptable end

Attach each one to the step where it branches: step 3 gets flow 3a. Number the sub-steps 3a1, 3a2. State where the flow ends or rejoins.

3a is the «extend» from your diagram — Join Waitlist. The two artifacts tell one story.

Alternative flows

3a. The course is full.

  1. 3a1. The system offers a place on the waitlist.
  2. 3a2. The student accepts. The system records the waitlist entry. The use case ends.
5

Add exceptional flows — the failures

Same numbering style. An exceptional flow ends without the goal. Always say what the system tells the actor.

Exceptional flows

2a. The prerequisites are not met.

  1. 2a1. The system rejects the request and shows the missing prerequisite [BR-1]. The use case ends.

One story, three endings — and every ending already appears in your postconditions from move 2.

6

Extract the business rules, delete the "how"

Read your flow again. Pull each policy out into a named rule. Then hunt for technology words — table, database, button, JSON, API — and delete them.

Business rules

BR-1 — A student cannot enroll in a course when its prerequisites are not met.

BR-2 — An enrollment is only possible while the course has free seats; otherwise only the waitlist is offered.

Red-pen list: how students lose marks here

  • Happy path polluted. "2. The system verifies prerequisites, and if they are not met it rejects…" — the branch belongs in 2a, not in step 2.
  • Failure filed as alternative. A rejection is exceptional. Only an acceptable outcome (waitlist) is alternative.
  • Trigger written as a precondition. "The student wants to enroll" is not a state; the submitted request is the trigger.
  • Implementation talk. Tables, SQL, screens, and buttons do not belong in a specification.
  • Postconditions for success only. Cover the waitlist and the rejection endings too.
  • Name mismatch. The spec name must equal the oval's name in the diagram.

Quick check

1 · "The member holds a valid membership card." Which section?

It is a state that must already be true before the use case starts — a precondition. The trigger is the event that starts the action.

2 · "When the course is full, the student can join the waitlist." Which flow type?

The waitlist is a defined, acceptable outcome, so this is an alternative flow. Compare: "prerequisites not met → reject" fails the goal, so it is exceptional.

3 · Which sentence does not belong in a use-case specification?

Tables and foreign keys are "how". The specification stays true under any technology — that is the what/how test.

4 · "A member can hold at most 5 loans at the same time." What is this?

It is a policy that exists without the software. The flow then gets a step "the system checks the loan limit [BR-2]" plus an exceptional flow for the violation.

5 · Where does the flow "3a. The course is full" attach?

The number before the letter names the branching step. 3a branches at step 3; its own sub-steps are 3a1, 3a2.

Now write on paper

Set a 8-minute timer. Write the full specification for Borrow Book, consistent with your Lesson 1 library diagram. Then grade yourself against the model.

Scenario. A member borrows books at a self-service kiosk. The member scans the membership card, and the system always verifies the membership. The member then scans a book, the system checks that the book can go on loan, records the loan, and shows the due date. Library policy: only valid members can borrow (BR-1); a member holds at most 5 loans at the same time (BR-2); the loan period is 21 days (BR-3). A member with several books repeats the scan for each book. An expired membership or a reached loan limit stops the process.

  3. The member scans a book.
  4. The system checks that the member can take another loan [BR-2].

Alternative flows

6a. The member has more books.

Exceptional flows

2a. The membership is invalid or expired.

  1. 2a1. The system rejects the member and shows the reason [BR-1]. The use case ends.

4a. The member reached the loan limit.

  1. 4a1. The system refuses the loan and shows the limit [BR-2]. The use case ends.
Postconditions
Success: each scanned book has a recorded loan with a due date. Failure: no new loan exists and the member saw the reason.
Business rules

BR-1 — Only a valid, unexpired membership can borrow.

BR-2 — A member holds at most 5 loans at the same time.

BR-3 — The loan period is 21 days.

Grade yourself

  • Name equals the oval from Lesson 1: "Borrow Book".
  • All nine sections present, in order.
  • Main flow is a clean happy path — no "if" inside it.
  • Repeat-scan handled as an alternative flow that rejoins at step 3.
  • Both failures written as exceptional flows attached to steps 2 and 4.
  • Three business rules named BR-1..3 and cited in the steps that check them.
  • Postconditions cover success and failure.
  • Zero technology words (kiosk hardware is the actor's channel and is fine; tables and databases are not).

Score 7–8: say "next" for Lesson 3. Score 5–6: rewrite the flows only. Score ≤ 4: redo the six moves with the enrollment example beside you.
